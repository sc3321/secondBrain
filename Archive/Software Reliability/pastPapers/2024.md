1a The Csmith paper says that “It is not difficult to generate random programs that
always terminate”. Nevertheless, Csmith was designed to allow non-terminating
programs to be generated, with a timeout being used when running the
programs. Discuss two main benefits of the design decision made in Csmith.

First of all, enforcing the feature of termination reduces the expressiveness of the types of programs that CSmith can generate. There are now objectively less programs and less program complexity that can be modelled. Secondly, although it may not be difficult, it is still an extra computation to enforce that every single generated program should terminate. This sort of property often has to be enforced formally and would require extra time in generation, thus limitting the amount of programs generated.

b Can the EMI approach introduce undefined behaviour via its metamorphic
transformations, causing it to report false positives?

Indeed this is possible and the purpose of EMI testing. Considering a P with input I, tested with a compiler, EMI approaches identify the regions of code of P not covered under execution with input I. Mutations on these dead code regions will lead to a host of different compiler optimisations between different compilers so when the mutated program P is run with input I, there could be differences in the output. These mutations may alter the flow of the program and make these sections of the code "live" opposed to dead, leading to an output that looks different. This would look like a bug but due to incorrect mutations, the programs P1..Pn are no longer equivelent.

iv) What kind of bugs would a grammar-based fuzzer miss that the smart (i.e.
input format aware) fuzzer we built in class would be able to find? Are
those bugs likely to be important?

In situations where we want to test things like divide by 0, or signed integer overflow or things of that nature which are specific to the program behaviour since we are dealing with a arithmetic program, the smart fuzzer would be more capable at detecting these things. Since it would be aware of the input format, it would be more likely to converge on these edge cases to do with the input. The grammar based fuzzer, is unlikely to land on these cases by accident. They would probably only detect issues with incorrect expression format, which is good but perhaps not that useful as the most important bugs are these edge cases described earlier which the programmer is less likely to be aware of him or herself.
